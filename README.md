## О проекте

MOKSUHUB — это не обычный каталог учебных материалов. Платформа объединяет обучение, практику, соревновательную механику и социальное взаимодействие в одном пространстве.

Пользователь может зарегистрироваться, изучать темы и курсы, решать задания по программированию, отправлять решения на проверку, проверять работы других участников, получать баллы, подниматься в рейтинге, открывать достижения, общаться в чатах и играть в соревновательные мини-игры.

Основной учебный цикл выглядит так:

```text
Изучить тему → решить задание → отправить решение → получить review
        ↑                                                    ↓
        └──── исправить ошибки ← комментарий ← проверка ────┘
```

Такой подход делает обучение активным: пользователь не только читает теорию, но и постоянно применяет её на практике.

## Архитектура приложения

```text
src/main.tsx
  ↓
src/App.tsx
  ↓
QueryClientProvider → AuthProvider → TooltipProvider
  ↓
BrowserRouter → Layout → Routes
  ↓
Pages → Hooks → Supabase client → Auth / Database / Realtime
```

`src/App.tsx` регистрирует маршруты. `Layout` задаёт общий каркас и навигацию. `AuthProvider` слушает состояние Supabase Auth и предоставляет текущую сессию. Hooks из `src/hooks` инкапсулируют запросы и бизнес-операции. Типизированный client находится в `src/integrations/supabase`.

Frontend отвечает за отображение и пользовательский ввод. Критические операции должны дополнительно проверяться в базе: принятие решения, начисление очков, завершение игры, изменение роли и выдача награды нельзя доверять только React-состоянию.

## Пользовательские сценарии

### Регистрация и вход

Пользователь открывает `/auth`, вводит email, пароль и никнейм. Supabase Auth создаёт учётную запись, а триггер базы создаёт профиль в публичной схеме. После входа пользователь получает доступ к функциональности согласно роли и ограничениям аккаунта.

### Изучение курса

На `/topics` пользователь выбирает маршрут, открывает обзор курса и переходит на страницу конкретного урока. Прогресс сохраняется на стороне интерфейса, а материалы отображаются через Markdown-компонент с поддержкой примеров кода и мобильной верстки.

### Решение и проверка

Пользователь читает условие, отправляет решение и отслеживает статус. Решение может попасть в очередь взаимной проверки. Проверяющий читает условие и код, выставляет результат и оставляет комментарий. При споре используется апелляция.

### Рейтинг и достижения

Принятые решения, выполненные проверки и другие события меняют статистику пользователя. Функции базы проверяют условия достижений и начисляют награды.

### Игра

Игрок выбирает режим, ставку и соперника либо принимает приглашение. Hook игры контролирует участника, очередь хода, статус матча, таймер, повторное действие и итог. Realtime позволяет обновлять состояние без ручного перезапуска страницы.

## Система заданий и проверки

Основной поток данных:

```text
tasks → solutions → reviews → status / points / appeals
```

`tasks` хранит условие, язык, сложность, категорию, очки и настройки. `solutions` связывает пользователя с заданием, содержимое решения и его статус. `reviews` хранит оценки и комментарии проверяющих. Апелляции позволяют пересмотреть спорный результат.

Для связи учебного контента и практики используется модель:

```text
Раздел курса → практическое задание → решение → review → статус → следующий раздел
```

Если связь с заданием не настроена, курс должен отображать понятное состояние, а не падать и не выдавать ложное подтверждение.

## Игровой раздел

Игры находятся на `/games`. Реализованные режимы включают крестики-нолики, камень-ножницы-бумагу, морской бой, русскую рулетку и «Четыре в ряд».

Для каждого режима необходимо контролировать участника, очередь, статус матча, диапазон хода, повторное действие, ничью, победу, таймер и завершение. Любая выплата или изменение результата должна подтверждаться сервером или SQL, а не только UI.

При добавлении игры нужно обновить типы, каталог, экран матча, realtime-подписку, приглашения, мобильную раскладку и проверку некорректных запросов.

## Профили, рейтинг и достижения

Профиль содержит никнейм, аватар, описание, активность, статистику, решения, проверки и достижения. Рейтинг отражает накопленные очки и активность. Badges зависят от условий: принятые решения, количество проверок, достижения по языкам и другие события. Автоматическое начисление выполняется функциями базы, чтобы пользователь не мог просто изменить значение в браузере.

Основные группы данных:

| Группа | Состав |
|---|---|

| Обучение | `tasks`, `solutions`, `reviews`, темы, курсы |
| Социальная часть | профили, лайки, сообщения, уведомления |

Не изменяйте уже применённую миграцию. Для новой схемы создавайте новую миграцию с новой временной меткой. Перед применением проверяйте внешние ключи, RLS и обратную совместимость hooks.

## Переменные окружения

Создайте локальный `.env`:

```env
VITE_SUPABASE_PROJECT_ID=your-project-id
VITE_SUPABASE_PUBLISHABLE_KEY=your-anon-or-publishable-key
VITE_SUPABASE_URL=https://your-project.supabase.co
```

| Переменная | Использование | Секрет |
|---|---|---|
| `VITE_SUPABASE_URL` | Публичный client | Нет сама по себе |
| `VITE_SUPABASE_PROJECT_ID` | Идентификатор проекта | Нет сама по себе |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный client | Нет при корректном RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | Только server-side | Да |
| `RESEND_API_KEY` | Только server-side email | Да |

Всё, что начинается с `VITE_`, потенциально попадает в браузерный bundle. Service-role key, пароли и приватные токены нельзя помещать в frontend.

pnpm exec tsc --noEmit

Перед pull request проверьте TypeScript, ESLint, production-сборку, основной маршрут, мобильный экран, RLS и отсутствие секретов в bundle.

## Деплой на Vercel

1. Подключите GitHub-репозиторий к Vercel.
2. Выберите preset `Vite`.
3. Укажите build command `pnpm build` или `npm run build`.
4. Укажите output directory `dist`.
5. Добавьте `VITE_SUPABASE_URL`, `VITE_SUPABASE_PROJECT_ID` и `VITE_SUPABASE_PUBLISHABLE_KEY`.
6. Выберите окружения Production, Preview и Development.
7. Выполните Deploy.
8. Проверьте `/`, `/auth`, `/topics`, `/tasks`, `/games` и маршрут курса.

Для прямого открытия `/topics` и `/courses/...` Vercel должен отдавать `index.html` для client-side маршрутов. Если прямой URL возвращает 404, настройте SPA rewrite на `/index.html`.

После изменения env требуется новый redeploy, потому что Vite встраивает `VITE_*` значения во время сборки.

## Разработка новых функций

### Новый экран

Создайте страницу в `src/pages`, добавьте маршрут, loading/empty/error-состояния и мобильную проверку.

### Новый запрос

Определите таблицу и RLS, затем создайте или обновите hook. Страница должна отвечать за отображение, а повторно используемая бизнес-логика — находиться в hook.

### Новый курс

## Диагностика

### `/topics` пустой

Откройте консоль браузера и исправляйте первую ошибку рендера. Частые причины — отсутствующий импорт hook/иконки, `undefined` в карточке или несовпадение структуры данных.

### Курс не открывается напрямую

Проверьте slug, маршруты `/courses/:slug` и `/courses/:slug/:lessonId`, а также SPA rewrite Vercel.

### Ошибка Supabase

Проверьте сессию, роль, имя таблицы, RLS-политику и применённую миграцию. Не исправляйте доступ публикацией service-role key во frontend.

### Игра не обновляется

Проверьте realtime-подписку, фильтр `match_id`, очистку subscription, `current_turn` и серверную проверку.

### Build падает

Запустите `pnpm exec tsc --noEmit`, затем `pnpm build`. Исправляйте первую ошибку в логе. Особое внимание уделяйте JSX, обратным кавычкам в примерах курса и отсутствующим импортам.

## Безопасность

RLS должен быть включён для пользовательских таблиц. Нужно проверять владельца строки, роль и допустимость операции. Критические состояния нельзя вычислять только на frontend.

Не храните в frontend service-role key, пароли, приватные токены и административные обходы. Если секрет опубликован в GitHub, переписке или bundle, его необходимо отозвать и создать новый.

Не создавайте скрытые backdoor-маршруты для смены пароля. Восстановление админского доступа должно проходить через официальный Supabase Auth и подтверждение владельца проекта.
